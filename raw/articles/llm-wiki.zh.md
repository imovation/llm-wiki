# LLM Wiki

使用 LLM 构建个人知识库的模式。

这是一个想法文档，旨在供你复制粘贴到自己的 LLM Agent（例如 OpenAI Codex、Claude Code、OpenCode/Pi 等）中使用。它的目标是传达高层理念，而你的 Agent 将与你协作构建出具体的实现。

## 核心理念

大多数人使用 LLM 处理文档的方式类似于 RAG：你上传一批文件，LLM 在查询时检索相关片段，然后生成答案。这确实可行，但 LLM 每次都在从头重新发现知识。没有积累。当你提出一个需要综合五份文档的微妙问题时，LLM 每次都必须找到并拼凑相关的片段。没有任何东西被构建起来。NotebookLM、ChatGPT 文件上传以及大多数 RAG 系统都是这样工作的。

这里的想法则不同。LLM 不是在查询时仅从原始文档中检索，而是**增量式地构建并维护一个持久的 wiki**——一个结构化的、相互链接的 Markdown 文件集合，位于你和原始源之间。当你添加一个新来源时，LLM 不仅仅是为后续检索做索引。它会阅读它，提取关键信息，并将其集成到现有的 wiki 中——更新实体页面、修订主题摘要、记录新数据与旧主张的矛盾之处、强化或质疑不断发展的综合结论。知识被一次性编译，然后*保持最新*，而不是在每次查询时重新推导。

这就是关键区别：**wiki 是一个持久的、不断积累的制品。** 交叉引用已经存在于其中。矛盾已经被标记。综合结论已经反映了你所阅读的一切。你每添加一个来源、每提出一个问题，wiki 都会变得更加丰富。

你从不（或很少）自己编写 wiki——LLM 编写并维护这一切。你负责寻找来源、探索和提出正确的问题。LLM 完成所有繁重的工作——摘要、交叉引用、归档和记账——这些工作让知识库随着时间推移真正变得有用。在实践中，我一边打开 LLM Agent，另一边打开 Obsidian。LLM 根据我们的对话进行编辑，而我实时浏览结果——跟随链接、查看图谱视图、阅读更新后的页面。Obsidian 是 IDE；LLM 是程序员；wiki 是代码库。

这可以应用于许多不同的场景。举几个例子：

- **个人**：追踪你的目标、健康、心理、自我提升——归档日记、文章、播客笔记，并逐步构建关于你自己的结构化画像。
- **研究**：在数周或数月内深入一个主题——阅读论文、文章、报告，并增量式地构建一个包含不断发展的论点的全面 wiki。
- **读书**：每读完一章就进行归档，为角色、主题、情节线索及其联系构建页面。最终你会得到一个丰富的伴读 wiki。想想像 [Tolkien Gateway](https://tolkiengateway.net/wiki/Main_Page) 这样的粉丝 wiki——数千个相互链接的页面覆盖角色、地点、事件、语言，由志愿者社区多年构建而成。你可以在阅读时亲自构建类似的东西，由 LLM 完成所有的交叉引用和维护工作。
- **商业/团队**：由 LLM 维护的内部 wiki，输入来源包括 Slack 线程、会议记录、项目文档、客户通话。可能有人类参与审核更新。wiki 保持最新，因为 LLM 完成了团队中没人想做的维护工作。
- **竞争分析、尽职调查、旅行规划、课程笔记、爱好深入研究**——任何你需要随时间积累知识并希望它们井井有条而不是散落各处的事情。

## 架构

分为三个层次：

**原始来源（Raw sources）**——你精心收集的源文档集合。文章、论文、图像、数据文件。这些是不可变的——LLM 从中读取但从不修改。这是你的事实来源。

**Wiki**——一个由 LLM 生成的 Markdown 文件目录。摘要、实体页面、概念页面、对比、概览、综合结论。LLM 完全拥有这一层。它创建页面，在新来源到来时更新它们，维护交叉引用，并保持一切一致性。你阅读它；LLM 编写它。

**模式（Schema）**——一份文档（例如 Claude Code 的 CLAUDE.md 或 Codex 的 AGENTS.md），告诉 LLM wiki 是如何组织的、有哪些约定、以及在摄取来源、回答问题或维护 wiki 时应该遵循什么工作流。这是关键的配置文件——正是它让 LLM 成为一个有纪律的 wiki 维护者，而不是一个通用的聊天机器人。你与 LLM 共同进化这份文档，逐步摸索出适合你领域的最佳实践。

## 操作

**摄取（Ingest）。** 你将一个新来源放入原始集合，并告诉 LLM 处理它。一个示例流程：LLM 读取来源，与你讨论关键要点，在 wiki 中写入一个摘要页面，更新索引，更新 wiki 中相关的实体和概念页面，并在日志中追加一条记录。单个来源可能涉及 10-15 个 wiki 页面。我个人倾向于一次摄取一个来源并保持参与——我阅读摘要、检查更新，并指导 LLM 应该强调什么。但你也可以批量摄取多个来源，只需较少的监督。由你来制定适合你风格的工作流，并将其记录在模式文档中以供未来会话使用。

**查询（Query）。** 你向 wiki 提出问题。LLM 搜索相关页面，阅读它们，并综合出一个带有引用的答案。答案可以根据问题的不同采取不同形式——一个 Markdown 页面、一个对比表格、一个幻灯片（Marp）、一个图表（matplotlib）、一个画布。重要的领悟是：**好的答案可以被归档回 wiki 中，成为新的页面。** 你要求的对比、一个分析、你发现的一个联系——这些都很宝贵，不应该消失在聊天历史中。这样，你的探索就会像摄入的来源一样在知识库中不断积累。

**检查（Lint）。** 定期让 LLM 对 wiki 进行健康检查。检查：页面之间的矛盾、已被新来源取代的过时主张、没有入链的孤立页面、被提及但缺少独立页面的重要概念、缺失的交叉引用、可以通过网络搜索填补的数据空白。LLM 擅长建议新的待研究问题和需要寻找的新来源。这能让 wiki 在成长过程中保持健康。

## 索引与日志

两个特殊文件帮助 LLM（和你）在 wiki 增长时导航。它们服务于不同的目的：

**index.md** 是面向内容的。它是 wiki 中所有内容的目录——每个页面都带有链接、一行摘要，以及可选的元数据，如日期或来源数量。按类别组织（实体、概念、来源等）。LLM 在每次摄取时都会更新它。在回答查询时，LLM 首先读取索引以找到相关页面，然后深入阅读它们。这在中等规模（约 100 个来源，约数百个页面）下出奇地好用，并且避免了对基于嵌入的 RAG 基础设施的需求。

**log.md** 是按时间顺序的。它是一个只追加的记录，记录发生了什么以及何时发生——摄取、查询、检查。一个有用的技巧：如果每条记录都以一致的前缀开头（例如 `## [2026-04-02] ingest | Article Title`），那么日志就可以用简单的 Unix 工具解析——`grep "^## \[" log.md | tail -5` 就能给出最近 5 条记录。日志为你提供了 wiki 演变的时间线，并帮助 LLM 了解最近做了什么。

## 可选：CLI 工具

在某个时候，你可能想构建一些小工具来帮助 LLM 更高效地操作 wiki。在 wiki 页面上进行搜索是最明显的一个——在小规模下索引文件就足够了，但随着 wiki 的增长，你需要合适的搜索功能。[qmd](https://github.com/tobi/qmd) 是一个不错的选择：它是一个用于 Markdown 文件的本地搜索引擎，具有混合 BM25/向量搜索和 LLM 重排序功能，全部在设备上运行。它既有 CLI（因此 LLM 可以 shell 调用它），也有 MCP 服务器（因此 LLM 可以将其作为原生工具使用）。你也可以自己构建更简单的东西——LLM 可以在需要时帮你 vibe-code 一个简单的搜索脚本。

## 技巧与提示

- **Obsidian Web Clipper** 是一个浏览器扩展，可以将网页文章转换为 Markdown。对于快速将来源加入原始集合非常有用。
- **本地下载图片。** 在 Obsidian 设置 → 文件与链接中，将"附件文件夹路径"设置为一个固定目录（例如 `raw/assets/`）。然后在设置 → 快捷键中，搜索"Download"找到"为当前文件下载附件"并绑定一个快捷键（例如 Ctrl+Shift+D）。剪藏文章后，按下快捷键，所有图片就会下载到本地磁盘。这是可选的但很有用——它让 LLM 可以直接查看和引用图片，而不是依赖可能失效的 URL。注意，LLM 无法一次性原生读取带有内联图片的 Markdown——解决方法是让 LLM 先阅读文本，然后单独查看部分或全部引用的图片以获取额外上下文。虽然有点笨拙，但效果还不错。
- **Obsidian 的图谱视图**是查看 wiki 形状的最佳方式——什么连接了什么，哪些页面是枢纽，哪些是孤岛。
- **Marp** 是一种基于 Markdown 的幻灯片格式。Obsidian 有对应的插件。可用于直接从 wiki 内容生成演示文稿。
- **Dataview** 是一个 Obsidian 插件，可以对页面的 frontmatter 运行查询。如果你的 LLM 为 wiki 页面添加了 YAML frontmatter（标签、日期、来源数量），Dataview 可以生成动态表格和列表。
- Wiki 只是一个 Markdown 文件的 git 仓库。你免费获得了版本历史、分支和协作功能。

## 为什么这可行

维护知识库的繁琐部分不在于阅读或思考——而在于记账。更新交叉引用、保持摘要最新、记录新数据何时与旧主张矛盾、保持数十个页面的一致性。人类放弃 wiki 是因为维护负担的增长速度超过了其价值。LLM 不会感到无聊，不会忘记更新交叉引用，并且可以在一次操作中触及 15 个文件。wiki 保持维护状态，因为维护成本几乎为零。

人类的工作是策划来源、指导分析、提出好问题，并思考这一切意味着什么。LLM 的工作是其他所有事情。

这个想法在精神上与 Vannevar Bush 的 Memex（1945 年）有相通之处——一个存储着文档间联想轨迹的个人化、精心策划的知识库。Bush 的愿景比后来的互联网更接近这个模式：私密的、主动策划的、文档之间的联系与文档本身同样宝贵。他无法解决的部分是谁来负责维护。LLM 解决了这个问题。

## 说明

本文档有意保持抽象。它描述的是理念，而非具体实现。确切的目录结构、模式约定、页面格式、工具——所有这些都取决于你的领域、你的偏好以及你选择的 LLM。上面提到的一切都是可选的、模块化的——选取有用的，忽略不需要的。例如：你的来源可能只有文本，因此你根本不需要图片处理。你的 wiki 可能足够小，索引文件就足够了，不需要搜索引擎。你可能不在乎幻灯片，只想要 Markdown 页面。你可能想要一套完全不同的输出格式。正确的使用方式是与你的 LLM Agent 分享本文，并共同协作实例化一个适合你需求的版本。本文的唯一工作是传达模式。你的 LLM 可以搞定剩下的部分。
