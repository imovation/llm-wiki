# 离职交接方案（AI 原生）

## 问题

开发同事离职，遗留项目后续需维护与扩展；后继者接手的是 AI 原生软件工程。如何无缝交接？

## 核心转变

传统交接痛点：文档过时、零散、互相矛盾。**AI 原生交接的核心不同：交接产物是给 Agent 读的，Agent 维护它。**

## 交接清单（离职前一周）

| 天 | 动作 | 产物 |
|---|---|---|
| 第 1-2 天 | **代码图谱冻结 + 质量门**：`codegraph init .` + 验证神节点/调用链/影响面；CI 门防 stale | `.codegraph/`（git 追踪），后继 Agent 首次打开即可精确查询 |
| 第 3-4 天 | **决策补齐（Spec 归档）**：`/opsx:propose "记录支付模块两阶段确认的设计决策"`… 用 Batch Spec 倒灌已有决策，`/opsx:archive` | `openspec/changes/archive/` 永久决策记录 |
| 第 5-6 天 | **知识编译（Wiki 构建）**：收集所有现存文档 + Spec 归档 → 喂 LLM Wiki 批量摄入 | `wiki/` 模块文档、实体关系、核心流程图 |
| 第 6 天 | **搜索就绪 + 入口文件**：`qmd collection add wiki` + embed；写 `AGENTS.md`/`CLAUDE.md` 入口 | 搜索 + agent 引导 |
| 第 7 天 | **验证交接**：clone 全新环境 → agent 跑通"读 wiki + 图谱 + 接需求"演练 | 交接通过 |

## 核心原则

1. **不写长篇文档**——离职同事口述，Agent 用 Spec 格式速记，重点是"为什么这么做"
2. **归档的 Spec 是 wiki 的 raw 源**——Spec 描述"应该"，wiki 编译为"事实"
3. **Batch Spec 结构**：proposal.md（覆盖范围/风险）+ specs/（各模块知识：支付坑、订单边界、部署配置）+ design.md（遗留架构视图）+ tasks.md（技术债清单）

## 为什么这套工具组合有效

即 [[llm-wiki-生态]] 里的全部工具，恰好构成交接方案：这些工具就是在解决"知识怎么不随人走"。**工具选型**：纯代码无文档 → CodeGraph；有遗留文档+设计图 → Graphify；需要长期理解沉淀 → LLM Wiki 模式。
